## 5.0

### Added
- Independent runtime Omni/frustum traversal and command-lane frame-synchronization settings. Optional synchronization completes the matching native frame before presentation, pins its camera pose/projection, and faults explicitly on timeout while retaining non-waiting graph-lock probes and bounded capture slices.
- Low-cost command-lane profiler markers for Tick, capture, publication, resource rebinding and frame commit.
- Graphical command-loop discussion document covering thread/lock boundaries, multi-frame buffer consumption, refresh triggering, current builder/factory differences, and Unity/DXGI presentation waits outside SDK access.
- [External reference index](docs/references/README.md) for the Vega and IRIS Performer observer, motion-model, and channel concepts, with a comparison to the CSW Observer requirements. The copyrighted documents are not stored in the repository.
- Command-driven map streaming through `MapStreamerHost`, with an ordered owned-buffer inbox, main-thread command consumption, and explicit native session teardown.
- Double-precision global camera snapshots, native camera-relative occurrence transforms, and a Unity hierarchy keyed by native node identity and the full unsigned 64-bit PathID.
- Presentation adapters for foliage, terrain-detail shading, and streaming diagnostics.
- Command-consumer, occurrence-identity, camera-snapshot, native texture-revision/lease, real GPU/shader, injected real-map lifecycle, and host map-URL precedence regression fixtures.
- Repeated real-map clear/reload and stop/start regression with retained native output, forced finalization, and assertions for drained buffers and released Unity resources.
- Clickable `setup.bat` and Git Bash `setup.sh` entry points for the locked .NET dependency-staging workflow.
- Parallel locked NuGet-to-Unity staging for `CSW.SceneManager` and GizmoSDK dependencies, with Windows x64 native validation, deterministic Unity plugin metadata, platform capability reporting, and owned cleanup.
- Lightweight per-frame and accumulated diagnostics for streamed mesh and texture counts, payload sizes, and build times.
- Constant-time texture diagnostics for active references, cache usage, peak usage, allocations, reuse, destruction, and discarded uploads.
- Optional F1 streaming diagnostics overlay with rolling frame, mesh, texture, and texture-cache statistics; F2 resets accumulated measurements and F3 toggles VSync.
- Accepted design and architecture requirements REQ-CSWU-SM-007–038 for the CSWUnity use of the C# CSW SceneManager, derived from how CSWUnreal uses the CSW SceneManager and accepted by acceptance decision AD-CSWU-001. They supersede REQ-CSWU-SM-001–006, REQ-CSWU-INIT-002, 003 and 007, and REQ-CSWU-SCENE-004. A [CSWUnreal SceneManager reference](docs/design/cswunreal-scenemanager-reference.md) records the analyzed CSWUnreal design and the differences from CSWUnity, and an [implementation-status ledger](docs/requirements/implementation-status.md) records the implementation progress of the Accepted requirements with evidence.
- Pending presentation-cadence requirement REQ-CSWU-PERF-009 for milestone M2: in unsynchronized presentation, every Unity frame presents streamed content for the camera pose of that frame, while occurrence and activation changes still wait for native frame commits.
- Accepted design and architecture requirements REQ-CSWU-SM-039–041, accepted by acceptance decision AD-CSWU-002. One session loads an ordered map list as in CSWUnreal; a map that SceneManager rejects is reported as a warning while the other maps stay presented; and a host setting selects synchronized presentation, which renders only camera views that SceneManager has processed, or unsynchronized presentation, which follows the camera at once and can show holes. They supersede REQ-CSWU-SM-031 and REQ-CSWU-SM-032 and resolve OD-CSWU-007. Pending REQ-CSWU-POS-003 proposes synchronized presentation as the default.
- Accepted design and architecture requirements REQ-CSWU-SM-042–044, accepted by acceptance decision AD-CSWU-003. As in CSWUnreal, CSWUnity refreshes continuously, also while the camera is stationary, and presents SceneManager output in its order, so that a level-of-detail transition shows no hole; in unsynchronized presentation the camera moves freely, and a camera change does not by itself submit a refresh. They supersede REQ-CSWU-SM-018 and REQ-CSWU-SM-041. The CSWUnreal SceneManager reference now describes how CSWUnreal processes level-of-detail transitions and records the activation scope as deviation 20.
- Accepted design and architecture requirement REQ-CSWU-SM-045, accepted by acceptance decision AD-CSWU-004. As in CSWUnreal, the per-update limits do not split a frame: the transforms and activations of a frame do not count toward the command limit, and a frame is processed in one Unity update. It supersedes REQ-CSWU-SM-017, and REQ-CSWU-SM-042 and REQ-CSWU-SM-044 now refer to it for frame synchronization.
- Accepted design and architecture requirements REQ-CSWU-SM-046 and REQ-CSWU-SM-047, accepted by acceptance decision AD-CSWU-005. Frame synchronization is pipelined as in the synchronous variant of CSWUnreal: each synchronized Unity update consumes the refresh that the previous update submitted through its `EndFrame` and then submits the next refresh, which SceneManager processes while Unity renders, and a wait that exceeds a timeout that the host can change at runtime faults. When the last host that holds the CSW platform stops streaming, it stops the GizmoSDK dynamic loaders and waits for their loads in progress before it releases the platform. They supersede REQ-CSWU-SM-045 and REQ-CSWU-SM-034. The CSWUnreal SceneManager reference now describes the synchronous variant of CSWUnreal and records the shutdown order of `CSW.Platform.Uninitialize` as an owner point.
- Accepted mechanism requirements REQ-CSWU-SM-048 for milestone M1 and REQ-CSWU-PERF-010 for milestone M2, accepted by acceptance decision AD-CSWU-006. GizmoSDK wrappers that CSWUnity obtains under edit access are released under that access with their finalization suppressed, so that the garbage collector never finalizes a wrapper whose release waits for edit access. Occurrences reuse GameObjects from two capped pools, one for occurrences without render resources and one for builder-realized occurrences that keep their mesh filter and mesh renderer, and the host fills the pools ahead of demand within a time budget for each update.
- `MapStreamerHost` settings `MaximumPooledObjects` (default 4096 for each pool), `PooledObjectReserve` (default 1024), and `PoolPrewarmTime` (default 0.001 s for each update), and the `UnityScene.PrewarmPools` method and the `GroupPoolDiagnostics` and `RenderablePoolDiagnostics` counters (REQ-CSWU-PERF-010).
- Accepted mechanism requirement REQ-CSWU-PERF-012 for milestone M2, accepted by acceptance decision AD-CSWU-006, which also resolves OD-CSWU-008. As in CSWUnreal, which registers a component when it builds it and only changes its visibility at an activation, the GameObject of a new occurrence is activated when the occurrence is created, with its rendering suppressed, and a frame commit shows and hides the occurrences of its frame together through `Renderer.forceRenderingOff` instead of activating and deactivating GameObjects. An occurrence that stays deactivated keeps an active GameObject until it is removed and its GameObject returns to its pool.
- Accepted mechanism requirements REQ-CSWU-SM-049 and REQ-CSWU-SM-050 for milestone M1, accepted by acceptance decision AD-CSWU-007. A camera renders the scene with a frustum that matches the camera of SceneManager, with a finite or an infinite far plane. Without omni traversal, the rendered frustum matches the frustum that SceneManager traverses, so that the culling of SceneManager and Unity agrees; with omni traversal, the views may differ, and the level-of-detail factor follows the zoom of the camera so that the level of detail still matches. The CSWUnreal SceneManager reference records the zoom scaling as deviation 21.
- `SceneManagerSettings` fields `InfiniteFarPlane` (default off), `LodFactor` (default 1), and `LodReferenceFieldOfView` (default 0, which leaves the factor unscaled), which the host can change at runtime, with the matching `CameraBridge.InfiniteFarPlane` and `CameraBridge.LodReferenceFieldOfView` properties. With an infinite far plane, CSWUnity submits the infinite far plane of `gzPerspCamera` with the near and far distances of the Unity camera, and Unity renders and culls with the projection of `gzPerspCamera` (`CameraBridge.NativeProjection`, `CameraRelativeFrame.Projection`) through the projection and culling matrices of the camera, without a change of its field of view or its near and far distances. Effects that derive depth from the camera, such as shadows and fog, still use its finite far clip plane, and the foliage module culls with the frustum and draw distance only, without Hi-Z occlusion, because the depth parameters that Unity derives for shaders do not linearize the depth of the infinite projection. With a reference field of view F between 0 and 180 degrees, the submitted level-of-detail factor is `LodFactor` multiplied by the zoom tan(F/2)/tan(V/2) for the vertical field of view V of the camera (`CameraBridge.EffectiveLodFactor`), as the effective level-of-detail factor of GizmoSDK (REQ-CSWU-SM-049, REQ-CSWU-SM-050).
- Demo flight in the example project. The `-csw-demo` argument or the `DemoFlight` component flies the camera of `MapStreamerHost` in a figure eight around the map origin at a constant ground speed, and **MapStreamer > Build Demo Player** builds a Windows player with `config.xml` and a `Start Demo.cmd` launcher. The `-csw-demo-speed`, `-csw-demo-size`, `-csw-demo-altitude`, `-csw-demo-pitch`, and `-csw-demo-infinite` arguments set the speed, size, height, view angle, and far plane of the flight.
- Fast full-motion PlayMode test of the real map (`NativeMapTests.FastFullMotionKeepsTheMapClosedSmoothAndFinalizerFree`). The camera flies a 12 s circle at about 300 m/s with changing height, heading, and pitch while each frame is rendered and read back. The test reports and limits holes where rays must hit the map, frame-time spikes, commit age, garbage collections and allocations per frame, and checks once a second that GC and finalizers finish while the main thread holds edit access (REQ-CSWU-SM-048), with a deliberate wrapper leak as a negative control. With `CSWUNITY_TEST_ARTIFACTS` set it writes a CSV of all frames and an image of the worst frame.
- `MapUrl` and `SceneManager/MapUrl` may contain GizmoSDK variables such as `%CSWUNITY_TEST_MAP%` and `$(key)`, which GizmoSDK expands when it loads the map.

### Changed
- `CSW.Unity.Camera` replaces `CameraBridge` and keeps its script GUID, and `CSW.Unity.CameraFrame` replaces `CameraRelativeFrame` (REQ-CSWU-PKG-015). An application can install its own camera through `CSW.Unity.MapControl.CameraFactory`, which creates a class derived from `CSW.Unity.Camera` for the view camera of the control. The derived class can override the pose, the field of view, the aspect ratio, the near and far distances, the far plane mode, the projection (`Projection`), the level-of-detail factor (`LodFactor`), sampling (`Sample`), presentation (`Present`, formerly the internal `PresentPose`), and commit (`Commit`). When `OwnsProjection` is true, by default when frames are synchronized or the far plane is infinite, the camera presents its projection again before the view camera renders; a camera that overrides the frustum should return true so that the rendered and the sampled frustum agree. Inside the `CSW.Unity` namespaces, an unqualified `Camera` now binds to `CSW.Unity.Camera`; write `UnityEngine.Camera` or add `using Camera = UnityEngine.Camera;` where the Unity camera is meant.
- `CSW.Unity.MapControl` replaces `MapStreamerHost` and keeps its script GUID, so saved scenes keep the component (REQ-CSWU-MM-001). `MapManager` becomes the internal class `CSW.Unity.StreamingMap.MapSession`, and the public `Manager` property is removed; read the map through `MapControl.State` (`MapControlState`, which replaces `MapManagerState`), `LoadedMapUrl`, `Error`, and `CompletedFrames`, and subscribe to `MapControl.Failed` and `MapControl.FrameCommitted`. Diagnostics read "CSW MapControl:" instead of "CSW Map Streamer:". The keyboard flight moves from the `FlightInput`, `FlightSpeed`, and `TurnSpeed` fields of the host to the separate component `CSW.Unity.FlightInput`, with `MapControl`, `Speed`, and `TurnSpeed`, which moves `MapControl.Camera`; `ExampleScene` adds it next to `MapControl`. Scenes that turned the built-in flight off need no change; scenes that used it must add `FlightInput`.
- `CSW.Unity.Factory` realizes GizmoSDK nodes in Unity, after `cswFactory` in CSWUnreal (REQ-CSWU-PKG-016). A static registry keyed by GizmoSDK type name selects the factory of the most specific native type that has one. The defaults are `NodeFactory` for `gzNode` and `gzGroup`, `TransformFactory`, `RoiNodeFactory`, `GeometryFactory`, `LodFactory`, `CrossboardFactory`, and `DynamicLoaderFactory`. `Register` returns false with a WARNING for a type that already has a factory, and `Unregister` returns false with a WARNING for a type that has none. An application replaces a default by unregistering it and registering a class derived from the built-in factory, whose `Capture` runs under edit access and whose `Construct`, `Update`, and `Destroy` run on the Unity thread for the pooled GameObject. `SceneCommandPump` no longer checks node types, and the `CanBuild` builder selection moves to `GeometryFactory`.
- `CSW.Unity.Conversion` performs every conversion between GizmoSDK and Unity values (REQ-CSWU-PKG-014). It replaces `UnityGizmoExtensions` and `GizmoUnityAxisMapping`, and `SceneCoordinateContext.Axes` is removed. Use `ToUnityPosition` and `ToGizmoPosition`, `ToUnityDirection` and `ToGizmoDirection` (formerly `ToNativeDirection`), `ToUnityNormal` and `ToGizmoNormal`, `ToUnityRotation` and `ToGizmoRotation` for heading, pitch, and roll in degrees, `ToUnityScale` and `ToGizmoScale`, and `ToUnityMatrix` and `ToGizmoMatrix`. `ToUnityPosition` takes only a local position: replace `Axes.ToUnityPosition(global, reference)` with `Conversion.ToUnityPosition(global - reference)`, which still subtracts in double precision. Plain component copies are renamed: `ToVector3` to `CopyVector3`, `ToVec3D` to `CopyVec3D`, `ToVec3` to `CopyVec3`, `ToMatrix4` to `CopyMatrix4`, and `ToMatrix4x4` to `CopyMatrix4x4`. `Axes.Basis` and `Axes.RootScale` become `Conversion.UnityBasis` and `Conversion.UnityRootScale`.
- `CSW.Unity.Platform` owns the platform startup (REQ-CSWU-PKG-013). The application starts and stops it through the static `Start(PlatformSettings)`, `Stop`, and `Update` methods, or with the default component `CSW.Unity.PlatformComponent`, which replaces `Saab.Unity.Initializer.Initializer` and keeps its script GUID, so existing scenes bind to it. Sessions take a reference with `Acquire`; the first reference initializes `CSW.Platform` and the Coordinate platform, and the last stops the dynamic loaders and releases them, which `MapStreamerHost` no longer does itself. `Stop` waits for the last reference. GizmoBase stays initialized until the process ends, because GizmoSDK does not register its message callback again after GizmoBase has been uninitialized. The `MessageLevel` setting filters GizmoSDK messages before they reach the Unity log. CSWUnity sends its own diagnostics as plain-text GizmoSDK messages from the sender `CSW.Unity` instead of writing to the Unity log, so the same level filters them (REQ-CSW-DIAG-001). Exceptions are sent at `FATAL` with their stack trace and appear as Unity errors instead of `LogType.Exception`. Routing to the Unity log starts with the first CSWUnity message, so failures before `Platform.Start` are still reported.
- The package code has moved to the CSW namespaces (REQ-CSWU-PKG-008, REQ-CSWU-PKG-010): the StreamingMap runtime, `MapStreamerHost`, `SceneManagerSettings`, and the `Interop` and `Modules` code are in `CSW.Unity.StreamingMap` under `Runtime/CSW.Unity.StreamingMap`, divided into `Commands`, `Coordinates`, `Diagnostics`, `Scene`, `Interop`, and `Modules`; the builders and managers are in `CSW.Unity` under `Runtime/CSW.Unity/Builders`; `CameraBridge` and `MapManager` are in `CSW.Unity`; the tests are in `CSW.Unity.Tests` and the demo in `CSW.Unity.Demo`. Code that uses `Saab.Foundation.Unity.MapStreamer*` must change its `using` directives. The assemblies `MAPSTREAMER`, `MAPSTREAMER.INTEROP`, `MAPSTREAMER.TESTS`, `MAPSTREAMER.PLAYMODE.TESTS`, `MAPSTREAMER.DEMO`, and `MAPSTREAMER.DEMO.EDITOR` are renamed to `CSW.Unity`, `CSW.Unity.StreamingMap.Interop`, `CSW.Unity.Tests`, `CSW.Unity.Tests.PlayMode`, `CSW.Unity.Demo`, and `CSW.Unity.Demo.Editor`; host assembly definitions that reference `MAPSTREAMER` must reference `CSW.Unity`.
- `MapStreamerHost` is the only streaming lane. It starts streaming in `Start`, after every `Awake` and `sceneLoaded` callback; a startup failure is logged and disables the component, disabling stops streaming, and re-enabling starts a new session.
- The host's map URL is the `StartStreaming` argument, otherwise its `MapUrl`, otherwise `SceneManager/MapUrl` in `config.xml`. The configured URL is read even when `ReadConfiguration` is false, which now only controls the other `config.xml` overrides; a missing URL fails startup with an error naming both sources.
- `Initializer` only initializes GizmoBase, message routing, monitoring, Android services, and the `config.xml` registry; it no longer locates or connects streaming and camera components.
- Optional foliage, terrain-shading, and diagnostics modules receive streamed content only through the host's `IScenePresentation`. Its events use the `SceneGameObjectHandler`, `SceneGameObjectReleaseHandler`, `SceneTraverseHandler`, and `SceneUpdateCameraHandler` delegates, and mesh and texture build diagnostics are read through `UnityScene` instead of `SceneManager` statics.
- Native traversal now defaults to Omni (`OmniView = true`), matching CSWUnreal. Frustum traversal leaves the map outside the camera frustum unloaded, which appears as holes in other views and in the main view while the camera turns.
- As in CSWUnreal, the per-update command and time limits no longer split a frame. They apply only outside frames, so a started frame is processed through its `EndFrame` without checking them, and the transforms and activations of a frame no longer count toward `MaximumCommandsPerTick` (REQ-CSWU-SM-045).
- Synchronized presentation (`SynchronizeFrames`) is pipelined as in the synchronous variant of CSWUnreal. Each synchronized Unity update completes the refresh that the previous update submitted through its `EndFrame` and then submits the refresh for its own camera pose, so SceneManager traverses while Unity renders and the presented camera is one update behind the requested pose. The new `Settings.FrameWaitTimeout`, in seconds and 5 by default, bounds the wait in each update and can change at runtime. An expired wait faults the session and clears the scene, and a value that is not positive and finite faults the next synchronized update (REQ-CSWU-SM-046).
- Command-lane resource publication uses mesh/state source-user indices instead of scanning every scene occurrence, including dependent states sharing refreshed textures and balanced cleanup on pooling.
- Removed occurrences return their GameObjects to their pools with the render resources detached and the renderer disabled, and reused GameObjects keep their mesh filter and mesh renderer instead of adding components again. A GameObject is destroyed only when its pool is full. In the Stensholm flight profile, this removed the `AddComponent` calls and GameObject destructions during the flight and reduced the managed allocation rate by about a fifth (REQ-CSWU-PERF-010).
- Frame commits no longer activate or deactivate GameObjects. As in CSWUnreal, `UnityScene` activates the GameObject of a new occurrence when it creates the occurrence, with `Renderer.forceRenderingOff` set, shows and hides occurrences and their descendants at frame commits only through that flag, and deactivates a GameObject when it returns to its pool. The new `SceneInstanceHandle.IsVisible` reports the committed visibility; code that used `activeSelf` or `activeInHierarchy` of an occurrence to decide whether it is shown must use `IsVisible`. Foliage culls and draws only the tiles of visible occurrences, so that a level-of-detail exchange never draws both levels. In the Stensholm flight profile, the longest frame commit fell from 11–20 ms to 2.5–4.4 ms and the longest update from 27–39 ms to 19.5–21 ms, with unchanged steady main-thread and GPU time (REQ-CSWU-PERF-012).
- `ExampleScene` contains only the `MapStreamerHost` composition, configured for the selected local Stensholm map with Inspector-owned map settings. Isolated same-version debug dependency staging is documented without changing the accepted package baseline.
- The Phase 1 command-driven lane uses matching local `CSW.SceneManager` and `cswSceneManager` packages `1.1.1.1-phase1.20261022.204509`, retaining the exact GizmoSDK `2.12.347.1` dependency baseline and requiring the matching managed, native, and bridge build.
- Established **CSW Map Streamer** (`csw-map-streamer`) as the name of the new generation while retaining existing `com.saab.map-streamer` identifiers during incremental migration.
- Pending requirement REQ-CSW-TERM-001 separates three names. **StreamingMap**, written as one word, is the CSW technology of streaming maps that provides the synthetic world with map data, and replaces "Streaming Map", "Map Streamer", and the working name CSW Map Streamer in new documentation and identifiers. `CSW.<Engine>.StreamingMap` is the API through which an engine realization exposes StreamingMap, and `CSW<Engine>` is the project that encapsulates the realization. Pending REQ-CSWU-PKG-010 names the StreamingMap API of CSWUnity `CSW.Unity.StreamingMap`, in `Runtime/CSW.Unity.StreamingMap`, and states that the `Saab.Foundation.Unity.MapStreamer` namespaces migrate to it; REQ-CSWU-PKG-008 now excludes the StreamingMap API from `CSW.Unity`. Existing `MapStreamer` and `map-streamer` identifiers remain until that migration.
- `SceneManagerSettings` moved into the `Saab.Foundation.Unity.MapStreamer.Csw` namespace with the other code that uses the CSW SceneManager; code that names the type must import that namespace. Serialized settings are unaffected. In code, the `Csw` folder and namespace carry the CSW name, so file and type names do not repeat it.
- Upgraded to Unity 6000.3.5f2
- Updated the staged dependency baseline to CSW.SceneManager 1.1.1.1 and GizmoSDK 2.12.347.1.
- Replaced the incomplete `vs17` installer and x64 batch scripts with the locked NuGet-to-UPM staging workflow.
- Replaced legacy geometry and texture streaming with the GizmoSDK GeometryExport and TextureExport APIs, writing directly into Unity mesh and texture storage for improved streaming performance.

Formats without that mapping retain direct `GraphicsFormat` uploads; CPU layout, mip chains and recycling remain validated.

Requirements use `REQ-CSWU-<AREA>-NNN` IDs with status, kind, milestone, use-case, and verification fields; Principle, Mechanism, and Class requirements are under `architecture/` and Behavior requirements under `functional/`. - Pending use cases UC-CSW-010–019 and requirements REQ-CSW-CV-003–016 in the [generic CSW baseline](docs/requirements/generic/requirements.md) describe how a programmer controls an Observer in the synthetic world. An Observer combines a View that shows what it sees and plays what it hears, a Camera that it carries relative to itself, a MotionModel that describes how it moves, and input that affects the movement. Application layers that use CSWUnity can add their own MotionModels, input sources, and interactions with the environment and its geometry, and connect them in the same way as the built-in ones. An Observer is placed on the ground or in a Reference Frame carried by a moving object, such as an aircraft, a helicopter, a ship, or a car, or by a part of it, such as a deck, a cabin, a building floor, a room, or a ladder. Reference Frames can be nested and supply the movement rules of the Observer, for example only up and down on a ladder. The Observer always has a global pose in the map coordinate system, and Views can show Cameras mounted on the Observer, such as a forward or a stabilized downward Camera. A View renders the 3D graphics as a virtual camera with its own render target, resolution, and projection. An Observer is steered through semantic input from a mouse, a keyboard, or another position device, and CSW provides UFO, flying-carpet, and orbital MotionModels for hovering and looking around, flying a steered path above the terrain, and circling a focus. The user can pick a house in the map as the focus and orbit it at a constant radial distance while it stays in the center of the View. An orbit looks straight down at 90° at most and never flips over, and the Observer can be kept above the ground and out of other geometry, with collision switched on or off per geometry type. A Reference Frame is distinct from the Local 3D Frame used for precision localization.
- Pending use cases UC-CSW-020–021 and requirements REQ-CSW-WC-001–003 in the [generic CSW baseline](docs/requirements/generic/requirements.md) describe how the application controls what the synthetic world contains geometrically. The world can contain several maps and models that are added, removed, shown, and hidden at runtime, and the application sets which map is shown where maps overlap. Rendering, surface placement, picking, and collision use the same combined geometry. Application layers that use CSWUnity can populate the world with their own static and moving objects, in large batches and from engine-native objects such as Unity GameObjects, and the objects become part of the world in the same way as built-in content.
- Pending use case UC-CSW-022 and requirement REQ-CSW-RC-001 in the [generic CSW baseline](docs/requirements/generic/requirements.md) let external code, from an application layer or another process, control how the 3D engine renders without access to its internals. Named parameters, such as LOD factor, view distance, quality profile, shadows, fog, lighting, wireframe, layer visibility, culling, and frame-rate limit, have the same meaning in every engine realization and apply to the whole world or to a single View. Changes take effect no later than the next frame, report the applied value, and report unsupported parameters without affecting the others.
- Pending use case UC-CSW-023 and requirement REQ-CSW-CV-017 in the [generic CSW baseline](docs/requirements/generic/requirements.md) add Frame Positions: positions in a Reference Frame, such as the frame in which an Observer moves, that SceneManager keeps valid when terrain detail streams in, a map is replaced, or the origin is rebased. Objects and Observers attached to a Frame Position follow it without the application moving them, and the Frame Position reports whether it is resolved, provisional, or unavailable.
- Pending requirements REQ-CSW-API-001 to REQ-CSW-API-016 in the [generic CSW baseline](docs/requirements/generic/requirements.md) and REQ-CSWU-PKG-008 and REQ-CSWU-PKG-009 in the [next-generation architecture](docs/requirements/architecture/next-generation-architecture.md) add API naming. Engine-independent CSW classes are named `CSW.<ClassName>`, like the existing `CSW.SceneManager` and `CSW.Platform`. They are delivered in `CSW.SceneManager`, either imported from the CSW repository's package or, before the CSW repository provides them, placed in a local engine-free `CSW.SceneManager` assembly. Classes that use Unity or the Unity API, including utilities, are named `CSW.Unity.<ClassName>`, and any future C# classes that control Unreal are named `CSW.Unreal.<ClassName>`. The engine-neutral Camera is `CSW.Camera` (`CSW::Camera` in C++); it exposes no engine camera type, and the engine realization connects it to the native camera. The generic position definition of the coordinate nomenclature is realized as `CSW.Position`, which succeeds `MapPos`. Its value is a global position, either a `GeoPosition` with its CRS or a Global 3D Position in a named frame, or a local position in a Local 3D Frame in which the map is realized, with the frame's identity and generation. It is floating, ground-clamped with a height above the ground that stays clamped while terrain detail streams in and reports whether it is resolved, or navigated: moved by a `CSW.Navigator` along a `CSW.Path`, like the Vega vgNavigator and vgPath. `CSW.Path` has linear or spline segments, is open or closed, and has a static origin or one relative to a moving object; `CSW.Navigator` starts, stops, resets, loops, follows simulation time, and raises waypoint events. It always states its Map Coordinate Context and is defined locally until the CSW repository provides it. The Observer is realized as `CSW.Observer` (`CSW::Observer` in C++), a camera carrier like the Vega vgObserver: it carries mounted `CSW.Camera` objects, has a `CSW.Position` and an orientation in its Reference Frame, and is moved by a MotionModel, by application code, by a `CSW.Navigator`, or by attaching it to a `CSW.Player` or another moving world object. The Player is realized as `CSW.Player` (`CSW::Player` in C++), a moving world object like the Vega vgPlayer: it has a `CSW.Position` and an orientation, whose placement mode makes it floating, ground-clamped, or navigated; it is moved by application code, a `CSW.Navigator`, a MotionModel, or an external simulation; it carries a Reference Frame to which Observers, Cameras, objects, and other Players are attached; it may have a visual model; and it is an entity of the Object API. Input sources are realized as `CSW.Input` (`CSW::Input` in C++), like the Vega vgIDev and the Gizmo3D `gzInputProvider`: a `CSW.Input` is fed by a device, a `CSW.Window`, a network command, or a recording, binds device input to named semantic actions at runtime, and delivers them to a `CSW.MotionModel` or to application code. The MotionModel is realized as `CSW.MotionModel` (`CSW::MotionModel` in C++), the same as the Vega vgMotion: it is attached to an Observer or a `CSW.Player`, provides the vgMotion types Spin, Drive, UFO, Warp, Fly, Trackball, Walk, Flight Simulator, Missile, PickFly, Device Direct, and user-defined types, with the CSW additions FlyingCarpet, a viewing type without flight dynamics, Rotorcraft for drones and helicopters, and Ballistic for unpowered projectiles, has an initial and a reset position, ground clamping with step height and depth for Walk, limits and collision, and runtime switching, and connects a `CSW.Navigator` to input by giving it only playback control such as pause and speed, so that its position still comes from the path. The map control of REQ-CSW-MM-001 and REQ-CSW-MM-002 is realized as `CSW.MapControl` (`CSW::MapControl` in C++), which succeeds the name MapManager: it controls the loading of maps and map parts through `CSW.SceneManager` without building scene objects itself, and keeps track of the projection, the extent, the maximum LOD, the LOD factor and view distance, the topology, the layers, and the load state that SceneManager reports for the loaded map; REQ-CSWU-MM-001 realizes it as `CSW.Unity.MapControl`, which succeeds the current `MapManager` class. The Unity realization of `CSW.Input` is `CSW.Unity.Input`, mapped to the Unity Input System; Unreal maps it to Enhanced Input. The View is realized as `CSW.View`, which corresponds to the Vega vgChannel: it takes its input from one `CSW.Camera`, which the application can switch at runtime, and draws what that Camera sees into a viewport region of the physical `CSW.Window` that it is placed in; it owns its viewport region and projection but no pixels of its own. The Window, named after the Gizmo3D `gzWindow`, is the render target that the application controls: an on-screen window or an offscreen image with one or more Views, its size, its refresh, image readback, and the input it receives. Unity realizes them with a `Camera` and its `rect` on a `Display` or `RenderTexture`, Unreal with a viewport region (`FSceneView`) of `UGameViewportClient` or a `USceneCaptureComponent2D`, and Gizmo3D with `gzWindow`, `gzImageRender`, or `gzTextureRender`. Pending REQ-CSWU-PKG-011 defines `CSW.Unity.Window`, the Unity realization that connects the window properties and Views of a `CSW.Window` to Unity rendering through `Display`, `RenderTexture`, and one Unity `Camera` per View, with on-request refresh, non-blocking readback, and window input. Pending REQ-CSWU-PKG-012 defines `CSW.Unity.Position`, a component and a utility method that place a GameObject at a `CSW.Position` through the Viewer Coordinate Mapping, follow ground clamping, navigation, and origin rebasing, and update navigated objects before the Cameras render. Engine-independent utilities, helper code, and small, simple classes are named `CSW.Utility.<ClassName>` and kept in a `CSW.Utility` folder. A broader library that is not engine-specific is in `CSW.Foundation` or in its own `CSW.<LibName>` namespace; a library that binds to the Unity API is in `CSW.Unity.Foundation` or `CSW.Unity.<LibName>`. REQ-CSW-API-007 places the engine segment directly after `CSW`: every class coupled to Unity is `CSW.Unity.<ClassName>` or `CSW.Unity.<LibName>.<ClassName>`, C# code specific to Unreal is `CSW.Unreal.<ClassName>`, and the engine realization of a generic class keeps its simple name, such as `CSW.Unity.Window` for `CSW.Window`; no namespace ends in an engine suffix such as `.Unity`. The existing `Saab.*` namespaces are not migrated yet.

### Fixed
- Geometry whose State has no active texture now uses the builder fallback material with the uniform color. The white placeholder texture no longer selects the terrain/asset shader, which ignores uniform color and needs presentation buffers, so untextured geometry with a uniform color is no longer invisible. A uniform vertex color on such geometry becomes the fallback material color, because the fallback shader ignores vertex colors.
- Stopping the last streaming host while a map is loading no longer ends the process with `std::bad_alloc`. The host stops the dynamic loaders and waits for their loads in progress before it releases the CSW platform, because `CSW.Platform.Uninitialize` unregisters the database managers before Gizmo3D stops the loaders (REQ-CSWU-SM-047).
- A frame commit no longer writes the field of view and the near and far distances of its refresh into the Unity camera. In unsynchronized presentation, a projection that the host changed was replaced by the projection of an older refresh and could alternate between the two (REQ-CSWU-SM-044, REQ-CSWU-SM-049).
- The private performance-validation dependency closure includes the GizmoSDK shutdown correction: deallocator joins no longer retain global graph EDIT access, preventing a captured real-map reload/shutdown deadlock while preserving guarded cleanup. The historical phase-1 setup baseline is unchanged.
- The non-waiting command lane now requires the matching CSW native thread-safe command/buffer reference cohort, preventing cross-thread lost references and native fast-fail without reintroducing global graph-lock waits. Document the isolated complete-cohort staging path separately from the historical phase-1 lock.
- Command-lane translation now presents the latest double global pose as a small camera offset from the committed native reference. ROI transforms and the camera rebase together without a visible catch-up step, while terrain and shader origins remain coherent.
- Command-lane camera rotation now follows the latest input every Unity frame instead of freezing until native EndFrame. Committing an older streaming frame preserves newer live rotation and the matching scene/shader reference.
- Command-lane Tick no longer waits for SDK graph access when submitting controls or polling output. Camera controls and refresh are queued with one trigger, and ordered frame changes share a non-waiting buffer-lock slice without retaining locks between Unity frames.
- Native command callbacks remain registered across full platform shutdown/reinitialization and collection of earlier managed lifetimes.
- Invalid occurrence transforms are rejected before allocating or consuming pooled Unity handles.
- Foliage placement shares GPU resources through balanced leases and releases temporary allocations when setup fails.
- Streamed color textures now respect the project's active Gamma or Linear color space, avoiding rejected uploads in Gamma projects while keeping feature and height textures non-sRGB.
- RGB24 map textures no longer become magenta on Direct3D 11 when native three-channel sampling is unsupported.
- Failed Unity texture construction no longer counts as a successful texture-cache creation.
- `FoliageModule` now skips initialization, Hi-Z generation, culling, and drawing when CAPS disables all tree and grass feature sets.
- Geometry streaming now accepts source meshes with multiple texture-coordinate units by explicitly exporting UV0 for the current Unity mesh layout.
- Newly loaded `RefNode` LOD branches remain inactive until native traversal reports them traversable, preventing out-of-range buildings from briefly appearing.
- UTM and SWEREF99 local orientation now follows true north instead of grid north by applying position-dependent meridian convergence from GizmoSDK. #413147
